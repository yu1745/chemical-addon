# 10 · 开发路线、测试与止损

## 1. 基线

当前代码事实由 `docs/progress.md` 定义。已有釜、池、结晶、过滤、分液、仪表、mixture、能量与 IPhreeqc 适配不可在新架构施工中静默回退。

## 2. 总体策略

先完善已有釜/池的玩法闭环，再实现炉，最后实现塔。理由：炉直接服务石灰和索尔维旗舰，塔的分段传质/蒸馏语义更复杂；但开发顺序不等于玩家最终解锁顺序。

## 3. 施工包 A：统一能力地基

### 水相引擎收敛优先项（2026-09）

按 `02-common-architecture.md` §3.1 执行：引擎状态与物料接口 → 游戏全面适配 → 统一化学数据 → 气液与热耦合。用户已授权破坏旧接口且明确不需要旧存档兼容；前两步共同构成本轮核心重构，不交付“物料一变就失效并回落旧四域重算”的过渡层。

核心验收：连续/分拍求解对照、新格式原样存档恢复、1 mB 探测与实际输送的比例一致性、不同水相混合、显式投料/抽料/蒸水的物料守恒、失败不吞料、共享会话不串釜。必须迁移真实调用链，禁止只增加无调用的抽象层。旧假量纲测试应改为引擎物理契约，不通过放宽断言掩盖错误。引擎与物流跨边界时末轮运行完整 `test`，通过后 `build -x test`，需要真实容器行为时追加一轮 GameTest。

后续计量收敛按 `02-common-architecture.md` §3.2：保留引擎内部介稳伪元素池；游戏使用真实公式，由引擎统一转换。新增验收包括伪池展开后的封闭反应原子守恒、界面外部原子流，以及同浓度不同水量的动力学比例一致性。不要把“消除补丁”误解为删除内部伪元素机制。

| 场景 | 断言依据 |
|---|---|
| 同一批次连续推进与分拍推进 | 相同速率模型、相同累计时间下，元素、溶剂、pH/pe及固相在数值容差内一致；中途不能重新指定酸碱或氧化态 |
| 从一桶取 1 mB，再取余量 | 两份化学库存之和等于原批次；抽样不触发额外反应；探测与真实抽取的标签一致 |
| 两批不同 pH/组成的液体混合 | 原生库存混合与游戏混合一致，pH/pe由求解产生，不按体积平均 |
| 存档后在新会话恢复 | 新格式恢复真实状态；不重新解释显示，也不触发存档时反应 |
| 外部投料及取出物料 | 操作由声明化学计量或比例取样定义；输入减量与输出增量对应，支持痕量、不重复结算 |
| 移除水 | 只按真实水库存及其 H/O 化学计量移除；不能同时按总流体比例移走溶质 |
| 缺模型、缺料、求解失败 | 候选态失败，容器、物品、气相及能源不提交半批结果；诊断指出具体失败 |
| 多釜交替求解 | 改变另一釜的物料与温度不影响本釜；共享会话的旧相、反应和温度对象不得残留 |

- 从现有 `vessel/` 明确共享几何、端口、材料与过程能力接口。
- 水相状态采用新格式，游戏接口适配引擎；本轮不保存旧 NBT 兼容。
- 建立配方所需能力标签，不再匹配现实机器 ID。
- 建立结构、端口和过程诊断协议。

验收：保留未被新引擎设计替代的玩法契约；新化学状态满足守恒、运输和失败事务要求。旧接口与存档不作为本轮约束。

既有结构层审计见 [`docs/audits/multiblock-migration-audit.md`](../docs/audits/multiblock-migration-audit.md)。水相重构按上述用户授权更新 NBT、物料与配方接口，不受历史 A1 的兼容限制。

## 4. 施工包 B：釜式可玩闭环

- 搅拌头、气体分布器、催化托盘。
- 液位、计量、状态与批次自动化。
- 釜式索尔维碳化，先批式后连续。
- 耐压/泄压最小能力。

验收：盐水精制批次＋索尔维碳化连续线；故障均可从世界内诊断。

### B2：过程控制层

- 统一 live-zero 仪表信号、流量/料层/过程状态与真实 pe/ORP。
- 试纸检测箱为特殊物种终点提供可校准模拟量。
- 相邻机架 PLC 提供传统指令和受限 Rhino JS 两种并行程序模式。
- 先以酸碱批次、沉淀过滤、气体吸收、氧化还原和结晶各做一条闭环验收，
  再扩充新的产业反应。

## 5. 施工包 C：池式工程化

- 面积负荷、清液溢流、底泥容量和浊度夹带。
- 自动排泥与过滤机联线。
- 将旧单方块过滤机迁移为固定三格动力专机：保留主机 ID/NBT，补滤板组、管汇端、方向化端口和世界内压紧动画。
- 中和或晶种分解第二用途。

验收：大小/流量关系量化；连续运行不积死；池不退化为大容量罐。

## 6. 施工包 D：炉式首个垂直切片

- 通用炉壳、耐火材料、固体/炉气库存、燃烧器和出料。
- 石灰、重碱、氢氧化铝煅烧。
- 炉气回收和欠烧/过热诊断。

验收：一套控制器跑三条配方；接入索尔维完整闭环。

## 7. 施工包 E：吸收能力收敛（已决策）

- 删除与“反应釜＋气体分布器”重复的吸收塔控制器、填料和无选择吸收模型。
- 气体吸收统一先走釜内守恒气液传质，再交给配方/IPhreeqc；吸收配方可要求 `gas_dispersed`，不得为单个气体另开设备路径。
- 流量、浸没、搅拌、分压和终点诊断在釜式部件上继续深化。

验收：外部气体不能绕过分布器；需要分散吸收的配方无分布器不运行；相同气体输入只存在一套化学语义。

## 8. 施工包 F：能源与专用模块

- 换热器、压缩机、电解槽。
- 温压/流量/能耗统一读数。
- 氯碱或合成氨垂直切片。

验收：多产物全部有出口与消费端；循环物料和废热真实降低成本。

## 9. 施工包 G：炉深化与未来分离设备复审

- 多级蒸馏等确有高度分段价值的机制另行论证；不得借吸收重新引入已删除的塔壳。
- 炉气氛、料层、熔融浴和炉渣分层。
- 接触法硫酸＋玻璃或一种金属示范线。

只有垂直切片通过后，才从 [08-industry-map.md](08-industry-map.md) 扩充内容。

## 10. 内容轨道

每条产业独立提交以下材料：产品与副产物用途、步骤图、四结构/专机映射、物种与配方、仪表终点、事故、自动化方案、Ponder、GameTest 和实机验收。没有消费端不得进入主线。

## 11. 测试层级

1. 纯 Java：守恒、定点量、能量、相分配、停留时间和分段模型。
2. GameTest：结构、能力、配方、拆损、同步和自动化。
3. 服务端冒烟：依赖、数据包、存档恢复和性能。
4. 客户端实机：成型提示、渲染、仪表、声音、粒子、Ponder 和真实 Create 管线。

`./gradlew build` 是每个施工包的最低门槛；相关测试必须零回归。

## 12. 性能预算

- 化学/过程低频结算；结构正常 tick 不扫描全部方块。
- 每种模板测试最小、最大和同区块多台。
- IPhreeqc 会话继续共享；塔段和炉料层采用聚合状态。
- 若连续模型无法在预算内稳定，先回退小批高频近似，不牺牲服务器稳定。

## 13. 止损条件

出现下列任一情况就暂停横向内容：

- 新设备只能提供速度倍率，没有新操作；
- 玩家无法从世界内信息诊断失败；
- 产品没有明确消费端；
- 需要新增第五种结构但不满足准入条件；
- 单条产业要求大量专机而不能复用；
- 最大结构或多台并行超出性能预算；
- 新格式物料守恒或实际玩法测试出现未解决的回归。模组未上线，不以旧存档兼容作为止损条件。

## 14. 文档纪律

- 设计只维护本目录十份文件，不创建隐性 archive 正本。
- 完成态只写 `docs/progress.md`。
- 施工时形成的具体数字、注册 ID 和配方表写入对应结构/产业文件，不复制到多个总表。
- 被否决的想法记录在相关章节的修订说明中，不保留整套旧计划继续参与决策。
